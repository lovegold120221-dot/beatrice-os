Three-layer layout under `lib/data/`:
- `models/` — immutable value objects (`Chat`, `DeviceProfile`, `Memory`, `Message`) with `fromJson` / optional `toJson` factories that map between JSON payloads and Dart types.
- `repositories/supabase_repository.dart` — single `SupabaseRepository` class wrapping a `SupabaseClient`, exposing CRUD methods for chats, messages, memories, device profiles, mobile agent settings, and image storage. All DB calls return `Map<String, dynamic>`; callers are expected to deserialize into the `models/` types.
- `services/` — domain services that compose the repository and external APIs. They fall into natural groups: AI backends (`gemini_service.dart`, `ollama_service.dart`, `hosted_planner_service.dart`, `opencode_service.dart`), mobile automation runtime (`mobile_use_agent_runtime.dart` orchestrating `MobileUseService`, `MobileTaskCoordinator`, and either Ollama or hosted planners), memory extraction (`memory_service.dart`), device/profile (`device_service.dart`, `profile_service.dart`, `language_preferences.dart`), media/OCR (`audio_service.dart`, `local_ocr_service.dart`, `object_detection_service.dart`), and platform helpers (`live_api_service.dart`, `web_lookup_service.dart`, `voice_opening_service.dart`).

Dependency direction is one-way: services depend on `SupabaseRepository`; models have no dependencies; the repository depends only on `supabase_flutter`. There are no interfaces — coupling is via direct class instantiation passed through constructors.
