Standard Flutter iOS project layout with three top-level components:
- `Flutter/` — generated Flutter build configuration (`Debug.xcconfig`, `Release.xcconfig`, `Generated.xcconfig`, `flutter_export_environment.sh`) plus the `AppFrameworkInfo.plist` declaring the embedded `io.flutter.flutter.app` framework. The `ephemeral/` directory holds LLDB helpers and environment files used during debugging.
- `Runner/` — the Xcode application target containing Swift entry points: `AppDelegate.swift` extends `FlutterAppDelegate` and implements `FlutterImplicitEngineDelegate` to register plugins via `GeneratedPluginRegistrant.register`; `SceneDelegate.swift` extends `FlutterSceneDelegate` for scene lifecycle; `Main.storyboard` hosts a `FlutterViewController` as the root view controller, and `LaunchScreen.storyboard` shows the launch image. `Info.plist` declares bundle metadata, permission descriptions (microphone, camera, photo library), and scene configuration pointing at the storyboard and SceneDelegate.
- `Runner.xcodeproj` / `Runner.xcworkspace` — Xcode project and workspace that bind the Runner target together with CocoaPods-managed dependencies.

Dependency direction is one-way: Runner depends on the Flutter framework and any pods declared in `Podfile`; Flutter-generated code (`GeneratedPluginRegistrant.h/.m`, `Generated.xcconfig`) flows into Runner but never back. The `Podfile` delegates dependency resolution to `flutter_tools/bin/podhelper` and enforces `use_frameworks!` so all pods are built as frameworks.
